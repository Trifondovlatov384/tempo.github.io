# Настройка фидов и шахматки в приложении «Нова»

Этот документ описывает, **что нужно сделать в приложении «Нова»**, чтобы работа с фидами и шахматкой была такой же, как в текущем приложении (real-estate). Код текущего приложения **менять не нужно** — это только инструкция для «Новы».

---

## 1. Как это устроено у нас (референс)

### 1.1. Общая схема

```
┌──────────────────┐     GET      ┌──────────────────┐     parse      ┌──────────────────┐
│  URL фида        │ ──────────►  │  XML (строка)    │ ────────────►  │  ProfitbaseOffer │
│  (Complex.       │   fetch()    │  от застройщика  │  parseProfit-  │ []               │
│   feedUrl)       │              │                  │  baseXml()     │                  │
└──────────────────┘              └──────────────────┘                └────────┬─────────┘
                                                                               │
                                                                               │ feedSync()
                                                                               ▼
┌──────────────────┐     prisma   ┌──────────────────┐
│  Building[]      │ ◄──────────  │  Группировка     │
│  Unit[]          │   create/    │  по houseName,   │
│  (MongoDB)       │   update     │  маппинг полей   │
└────────┬─────────┘              └──────────────────┘
         │
         │ getBuilding() → Unit[] для списка/шахматки
         ▼
┌──────────────────┐
│  Список /        │  Всё, что видит пользователь, идёт из БД.
│  Шахматка        │  Фиды только наполняют/обновляют БД.
└──────────────────┘
```

**Главное:** фид загружается по HTTPS, парсится в единый формат офферов, затем данные пишутся в БД (Building, Unit). Список и шахматка **всегда читают из БД**, не из фида напрямую.

### 1.2. Загрузка фида у нас

- **Метод:** обычный `fetch(feedUrl, { signal, headers: { Accept: "application/xml, text/xml, */*" } })`.
- **Таймаут:** 60 секунд.
- **Лимит размера:** 50 MB.
- **Без** кастомного HTTPS-агента и без axios для самого запроса фида.

Если у вас в «Нове» запрос выполняется **на сервере (VPS)** и при этом возникает SSL-ошибка при обращении к Profitbase — это отдельная проблема окружения (см. раздел 3).

## 2. Что должно быть в приложении «Нова»

### 2.1. Модели данных (Prisma / БД)

У комплекса (Complex) должны быть поля:

| Поле              | Тип     | Назначение |
|-------------------|--------|------------|
| `feedUrl`         | String? | URL фида (только HTTPS, например `https://pb20127.profitbase.ru/export/profitbase_xml/...`) |
| `feedComplexName` | String? | Для фидов с несколькими комплексами (RZV, CIAN) — название комплекса в фиде для фильтрации офферов |

У корпуса (Building): `name`, `handOverDate`, `chessOrderBy` (сортировка в шахматке: number | area | price | type).

У юнита (Unit): `number`, `floor`, `type`, `area`, `price`, `pricePerM2`, `view`, `image`, `status` (коды: `available`, `sold`, `paid_reservation`, `free_reservation`, `closed_for_sale` и т.д.), связь с `buildingId` и `rcId`.

### 2.2. Парсер XML

- Один парсер с **автоопределением формата** по корневому элементу:
  - `realty-feed` → Profitbase (плоский список `<offer>`).
  - `complexes` → Domclick (complex → buildings → building → flats).
  - При необходимости — RZV/Grad, CIAN (как в нашем `parseProfitbaseXml.ts`).
- Выход парсера — единый массив офферов (например, `ProfitbaseOffer[]`) с полями: `houseName`, `number`, `floor`, `price`, `area`, `pricePerM2`, `statusHumanized` / `status`, `imagePlan`, `windowView`, `rooms`, `propertyType`, `builtYear`, `readyQuarter`, `objectName` (для фильтра по `feedComplexName`).

Можно взять за основу логику из нашего репозитория: `src/lib/parseProfitbaseXml.ts` (типы, маппинг статусов, обрезка длинных строк до 2000 символов при записи в БД).

### 2.3. Синхронизация (Server Action / API)

Алгоритм `feedSync(rcId)`:

1. Проверка прав (только редактор/админ комплекса).
2. Получение комплекса с `feedUrl` и `feedComplexName`.
3. **Загрузка XML** по `feedUrl` (GET, таймаут 60 с, лимит 50 MB, заголовок `Accept: application/xml, text/xml, */*`).
4. Парсинг XML → массив офферов.
5. При наличии `feedComplexName` — фильтрация офферов по полю «название комплекса в фиде».
6. Группировка по корпусу (`houseName`), дедупликация по (корпус, номер) — оставлять последний оффер.
7. Для каждого корпуса: найти или создать Building, обновить `handOverDate` из фида.
8. Для каждого оффера: найти Unit по (rcId, buildingId, number); если есть — обновить поля из оффера, если нет — создать. Маппинг статусов из текста фида в коды (`available`, `sold` и т.д.).
9. После записи: `revalidatePath` по страницам комплекса и корпусов.

Лимит: не более 100 000 офферов за один запуск.

### 2.4. UI

- На странице комплекса: поле «URL фида Profitbase» (редактируемое), поле «Название комплекса в фиде» (опционально), кнопка **«Обновить из фида»**.
- Кнопка вызывает `feedSync(rcId)` и после успешного ответа делает `router.refresh()`.
- Вывод результата: при успехе — количество созданных корпусов/юнитов и обновлённых юнитов; при ошибке — текст ошибки (в т.ч. «Не удалось загрузить фид: …»).

### 2.5. Шахматка

- Данные для шахматки берутся **только из БД**: выборка `Unit` по корпусу (buildingId).
- Построение сетки: группировка юнитов по `floor`, этажи по убыванию, на каждом этаже сортировка по выбранному полю (`chessOrderBy`: number / area / price / type).
- Отображение: строки = этажи, ячейки = юниты (номер, площадь, цена, статус и т.д.). Пустые ячейки для выравнивания сетки.

У нас это реализовано в `src/lib/chessboardGrid.ts` (`buildChessGrid`) и в компоненте шахматки по корпусу (UnitChessboard), который получает уже загруженные `Unit[]` из БД.

## 3. SSL/TLS при загрузке фида с VPS (Profitbase)

### 3.1. В чём проблема

При нажатии «Обновить из фида» в «Нове» запрос к фиду выполняется **на сервере** (VPS → сервер Profitbase). Во время TLS-рукопожатия сервер Profitbase присылает **TLS alert internal_error (код 80)** и обрывает соединение.

Точная ошибка OpenSSL:

```text
80ACAED41E7E0000:error:0A000438:SSL routines:ssl3_read_bytes:tlsv1 alert internal error:../deps/openssl/openssl/ssl/record/rec_layer_s3.c:1601:SSL alert number 80
```

То есть проблема именно в **исходящем HTTPS-запросе с VPS к домену Profitbase**, а не в том, что сайт «Новы» открывается по HTTP или нет домена.

**Важно:** если в «Нову» подставлен **тот же URL фида**, что и в нашем приложении (где фид успешно качается), а ошибка 80 всё равно появляется — значит, дело **не в фиде и не в URL**, а в **окружении**, где выполняется запрос. У нас запрос идёт из одной среды (например, другой хостинг или локально), в «Нове» — с VPS с другим Node/OpenSSL или с другой сетью. Profitbase в ответ на Client Hello с этого VPS присылает internal_error и рвёт соединение. Поэтому устранять нужно именно на стороне «Новы»/VPS: диагностика (curl, версии) → один из обходных вариантов из раздела 3.4.

### 3.2. Что уже можно было сделать в «Нове»

- Загрузка только по HTTPS (без file://).
- Использование встроенного `https` с явным `servername` (SNI) или axios с кастомным `https.Agent` (TLS 1.2, servername, rejectUnauthorized: true, таймаут 60 с, User-Agent и Accept).

Если после этого ошибка сохраняется — значит, либо окружение VPS/хостинга, либо политика Profitbase.

### 3.3. Что проверить на VPS в первую очередь

1. **Проверка с сервера через curl**
   - Выполнить на VPS:
     ```bash
     curl -v "https://pb20127.profitbase.ru/export/profitbase_xml/..."
     ```
     (подставить реальный URL фида из .env или из настроек комплекса.)
   - Если **curl тоже падает с SSL** — проблема сетевая/хостинг или ограничения со стороны Profitbase (IP, регион, датацентр).
   - Если **curl успешен** — TLS с Node.js на этом же сервере ведёт себя иначе (другой Client Hello); тогда имеет смысл подбирать настройки TLS в Node (см. ниже).

2. **Версии окружения**
   - На VPS выполнить: `node -v`, `openssl version`.
   - Зафиксировать их для передачи второму программисту или в поддержку хостинга/Profitbase.

### 3.4. Варианты решения в коде «Новы»

**Вариант A: Оставить fetch, но убедиться, что запрос идёт в нужном окружении**

- У нас загрузка фида делается обычным `fetch()`. Если у вас приложение на VPS работает в среде, где Node/OpenSSL дают другой Client Hello, и Profitbase на него отвечает internal_error, то один только переход на fetch это не исправит — нужны шаги ниже.

**Вариант B: Загрузка фида через axios с кастомным https.Agent (в «Нове»)**

- Установить axios, в Server Action (или месте, где качаете фид) использовать `axios.get(feedUrl, { ... })` с кастомным агентом:
  - `https.Agent` с `minVersion: "TLSv1.2"`, `maxVersion: "TLSv1.2"`, `servername: url.hostname` (из разобранного `feedUrl`), `rejectUnauthorized: true`.
  - Таймаут 60 с, заголовки `Accept: application/xml, text/xml, */*`, при необходимости `User-Agent`.
- Если ошибка остаётся — пробовать другой набор cipher suites или другую версию Node/OpenSSL на VPS.

**Вариант C: Прокси**

- Если на хостинге есть HTTP-прокси для исходящих запросов, через который TLS к Profitbase успешен (например, curl через тот же прокси работает), то в «Нове» настроить загрузку фида через этот прокси (в Node это делается через `HTTPS_PROXY` / опции агента с `proxy`).

**Вариант D: Внешний сервис**

- Вынести загрузку фида в отдельный сервис/функцию (другой хостинг, другой регион или сеть), который по запросу качает XML и отдаёт его вашей «Нове» (по внутреннему API или по защищённому каналу). Тогда TLS к Profitbase происходит не с VPS «Новы», а с другой среды, где рукопожатие может проходить успешно.

### 3.5. Что обсудить со вторым программистом / хостингом / Profitbase

- Может ли сервер Profitbase **не принимать** рукопожатие от этого клиента (набор шифров/расширения от Node/OpenSSL на VPS, ограничения по IP/User-Agent).
- Не режет ли **прокси/фаервол на стороне хостинга** исходящий HTTPS (подмена сертификатов, фильтрация по SNI).
- Отличается ли поведение **версии OpenSSL/Node на VPS** (другой Client Hello) и не блокирует ли Profitbase такие клиенты.
- Есть ли **ограничения по IP/региону/датацентру** со стороны Profitbase.

### 3.6. Жёсткое требование

Фид должен подгружаться **только по HTTPS-ссылке** на фид (без обходного варианта через сохранение в файл по file:// на сервере).

## 4. Краткий чеклист для «Новы»

| № | Что сделать |
|---|-------------|
| 1 | В модели комплекса: поля `feedUrl`, `feedComplexName`. В модели Building: `name`, `handOverDate`, `chessOrderBy`. В модели Unit: поля как в разделе 2.1. |
| 2 | Реализовать парсер XML с автоопределением формата (Profitbase, Domclick, при необходимости RZV/CIAN) и маппингом в единый тип оффера и статусов. |
| 3 | Реализовать Server Action (или API) `feedSync(rcId)`: загрузка по feedUrl → парсинг → группировка по корпусам → создание/обновление Building и Unit → revalidatePath. |
| 4 | UI: блок с полем URL фида, полем «Название комплекса в фиде», кнопкой «Обновить из фида» и выводом результата синхронизации. |
| 5 | Шахматка: данные только из БД (Unit по корпусу), построение сетки по этажам и выбранной сортировке. |
| 6 | Если на VPS при загрузке фида возникает SSL alert internal_error: проверить curl и версии Node/OpenSSL на VPS; при необходимости использовать axios с https.Agent (TLS 1.2, SNI), прокси или вынос загрузки во внешний сервис; согласовать с хостингом и Profitbase. |

После выполнения пунктов 1–5 логика фидов и шахматки в «Нове» будет соответствовать нашей; пункт 6 нужен именно для устранения SSL-ошибки на VPS при обращении к Profitbase.
